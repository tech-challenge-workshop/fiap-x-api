## Findings (ranked)

### F1 — Medium — A refused completion becomes a permanent 502, and the upload is never discarded
- **Where**: `src/storage/s3-upload-storage.ts:188-193` maps every non-`NoSuchUpload` error from `CompleteMultipartUpload` to `StorageUnavailableError`. `src/uploads/complete-upload.service.ts:78-82` then propagates it.
- **Scenario (reproduced on RustFS 1.0.0 through the API)**:
  1. Declare 20 MiB, then PUT 1 byte to part 1 and 4 MiB to part 2.
  2. Confirm → `502 {"message":"Storage unavailable"}`. The retry gives 502 again.
  3. Storage afterwards: 1 multipart upload still in progress, 0 objects.
- **Why it matters**:
  - The declared and real sizes differ, yet the client gets neither the 400 of P2.6 nor any discard.
  - P2.10 reserves 502 for storage that is unreachable, and here storage answered.
  - A client cannot tell this from an outage and retries forever. The parts sit in the bucket until the 1-day lifecycle rule.
  - The same applies to `InvalidPart` / `InvalidPartOrder`.
  - The in-memory double throws a plain `Error('InvalidPart')` (`in-memory-upload-storage.ts:133`), so e2e would show 500 and cannot surface this.
- **Fix task**:
  1. In `complete()`, map `EntityTooSmall`, `InvalidPart` and `InvalidPartOrder` to a new outcome, for example `'rejected'`.
  2. For that outcome, the service aborts the multipart upload and answers 400 naming the size.
  3. Add a RustFS integration case and an e2e case.

### F2 — Low/Medium — The UPL-10 log tests cannot see `console.*`
- **Where**: `test/support/capturing-logger.ts` captures only Nest's `LoggerService`. The assertions are at `start-upload.e2e-spec.ts:295-310` and `download.e2e-spec.ts:239-257`.
- **Scenario**: a later change adds `console.log(url)` in `StartUploadService` or `DownloadService`. The full build gate stays green (M08b and M08d survive). ESLint has no `no-console` rule, and the lint run on the mutant exited 0. A presigned URL then lands in container logs.
- **Fix task**: add `no-console` to ESLint for `src/`, or have the log tests also spy on `process.stdout.write` and `process.stderr.write`.

### F3 — Low/Medium — No test pins "internal calls use the internal client"
- **Where**: `s3-upload-storage.ts:75-81`, and the test setup at `test/s3-upload-storage.e2e-spec.ts:53-60`.
- **Scenario**: `fromConfig` builds the call client from `publicEndpoint` (M22). The suite's two endpoints are loopback aliases of one server, so everything passes. In compose, the public endpoint (the host's `localhost:<port>`) is unreachable from the API container, so every start and confirmation answers 502. Only the platform smoke would catch it.
- **Fix task**: add a unit test that builds `S3UploadStorage` with a recording `S3Sender` and a separate presigner. It asserts that every non-presign method goes through the sender and that the presigner's `send` is never called.

### F4 — Low — The `findObject` NotFound-after-list branch is untested
- **Where**: `s3-upload-storage.ts:219-223`.
- **Scenario**: a concurrent size-mismatch confirmation deletes the object between `ListObjectsV2` and `HeadObject`. The intended 404 would become 502 with no failing test (M32). This is a narrow race.
- **Fix task**: a unit test with a stub sender that answers the listing and then a 404 head.

### F5 — Low — The design's "printable ASCII" key rule is untested
- **Where**: `complete-upload.service.ts:20,55`. The spec requires only missing/blank → 400; the design adds "malformed".
- **Scenario**: the charset restriction is dropped (M33) and a latin1 or non-ASCII key reaches the Catalog. No test fails.
- **Fix task**: an e2e test sending a non-printable-ASCII key (for example `chave-é`) that expects 400 and no storage contact.

### F6 — Low (spec-precision gap) — A second key on the same upload creates a second request
- **Where**: the Catalog dedups only by `(owner, idempotencyKey)` (`processing-catalog/src/application/create-processing-request.use-case.ts`). The API has no per-upload guard: `complete-upload.service.ts:97` calls create on every confirmation of an existing object.
- **Scenario**: a client loses the response to its confirmation with K1 and retries with a newly generated K2. It gets 201 and a second request for the same object, so the video is processed twice.
- **Spec status**: P2.3 covers only the same key, so the code conforms. The Goal line "exactly one Processing Request per confirmation, however many times the confirmation is retried" is ambiguous here.
- **Decide in spec**: either accept this, or bind the key to the upload (object metadata, or a Catalog constraint on `(owner, sourceStorageKey)`).

### F7 — Info (spec-precision gap) — `contentType` is matched case-sensitively
- **Where**: `start-upload.dto.ts:34`. `Video/MP4` → 400, while RFC 2045 MIME types are case-insensitive.
- **Spec status**: the spec lists the lowercase literals, so the code conforms. This repeats candidate lesson L-007 (state the case rule for protocol tokens).
- **Action**: record the rule in the spec.

### F8 — Info — The upload 404 body is `"Upload not found"`
- **Judgement**: P2.8 requires only 404, and the body is constant across all four causes (byte-identical, `complete-upload.e2e-spec.ts:268-270`), so no existence oracle exists. Design said the S5 constant 404 would be "reused". This is a wording drift from design, not a spec violation. The download route does use S5's body, as P3.4 requires. **Accepted.**

### F9 — Info (pre-existing, outside the diff) — The local in-memory Catalog fallback leaks the key
- **Where**: when `CATALOG_BASE_URL` is unset, `processing-requests.module.ts:13-18` silently binds `InMemoryCatalogClient`. Its ids embed the source key (`in-memory-catalog-client.adapter.ts:64`).
- **Effect**: in that mode the generated key reaches clients inside `processingRequestId` and inside the download file name. Observed: `frames-pr-alice-sources/alice/<uuid>.mp4-1.zip`.
- **Scope**: unreachable with the real Catalog. It is noted because S6 makes the key server-owned.
