# Upload and Download Specification — api

## Problem Statement

A user still cannot send a video or receive a ZIP. `POST /processing-requests` takes a `sourceStorageKey` the client makes up, so the video must already be in storage by some other means, and an authenticated user can name another user's object and receive its frames — the known risk S5 recorded. Nothing issues a download either: the ZIP the Worker produces is unreachable to its owner.

This slice gives the API the product's real edges: it issues presigned multipart URLs so the client uploads straight to object storage, confirms the upload idempotently and creates the Processing Request from a key it generated itself, and issues a short-lived download URL to the owner of a completed request.

## Goals

- [ ] An authenticated user uploads an MP4 or MOV of up to 500 MB and gets exactly one Processing Request per confirmation, however many times the confirmation is retried
- [ ] Every source key is generated by the API under the caller's identity; no client-supplied key reaches the Catalog
- [ ] The owner of a completed request downloads its ZIP through a short-lived URL, and nobody else can obtain one

## Out of Scope

| Feature | Reason |
| --- | --- |
| Storage topology, credentials, public endpoint, bucket lifecycle | `fiap-x-platform` (UPL-15 to UPL-18) |
| Durable idempotency and the archive-key lookup | `processing-catalog` (UPL-11 to UPL-14) |
| Validating the file's real content (codec, duration, integrity) | The Worker's FFprobe validation (S4) |
| Cancelling or resuming an upload | context.md, Deferred Ideas |
| Sharing, reprocessing | Out of scope in the gap analysis |
| Email notification | S7 |

| Who reports the parts | The API lists them in storage on confirmation; the client sends no ETags | Discussed: simplest client, nothing about the parts is taken on trust | y |
| Declared vs real size | A mismatch is rejected at confirmation (400), the upload discarded, no request created | Discussed: otherwise the 500 MB limit is decorative | y |

| Download response | `GET /processing-requests/:id/download` → `200 {url, expiresAt}`; not `COMPLETED` → 409; another owner's or missing → 404 as in S5 | Discussed | y |
| The S5 create endpoint | Removed | Discussed: it is the path that lets a user name another user's object | y |
| Accepted types | Extension `.mp4` or `.mov` (case-insensitive) **and** `contentType` `video/mp4` or `video/quicktime` matching that extension | `docs/foudation.md`: the API pre-validates extension and MIME type; a mismatch between them is itself a sign the declaration is wrong | y |
| Size bounds | `sizeBytes` an integer from 1 to 524 288 000 (500 MiB) | `docs/foudation.md` 500 MB, read as binary megabytes like the Worker's `MAX_SOURCE_BYTES` | y |

| Who may confirm an upload | Only the user who started it; anyone else's `uploadId` → 404 | Same non-disclosure rule as S5's reads | y |
| Storage unreachable | `502`, like the Catalog | One contract for "a dependency failed" | y |

## User Stories

### P1: Start an upload ⭐ MVP

**User Story**: As a user, I want the API to give me upload URLs for my video so that I can send it straight to storage.

**Why P1**: Nothing else in the product can start without it.

**Acceptance Criteria**:

1. WHEN an authenticated user calls `POST /uploads` with a valid `fileName`, `contentType` and `sizeBytes` THEN the API SHALL respond `201` with `uploadId`, `partSize` (16 777 216), one `{partNumber, url}` per part numbered from 1 to `ceil(sizeBytes / partSize)`, and `expiresAt` one hour ahead.
2. WHEN an upload is started THEN its object key SHALL be `sources/<sub>/<uuid>.<ext>`, generated by the API, with `<ext>` the lowercase extension of `fileName`.
3. The response SHALL NOT contain the object key as a field.
4. IF `fileName` does not end in `.mp4` or `.mov` (case-insensitive) THEN the API SHALL respond `400` naming `fileName`.
5. IF `contentType` is not `video/mp4` for `.mp4` or `video/quicktime` for `.mov` THEN the API SHALL respond `400` naming `contentType`.
6. IF `sizeBytes` is not an integer from 1 to 524 288 000 THEN the API SHALL respond `400` naming `sizeBytes` and its range.
7. IF the request has no valid token THEN the API SHALL respond `401` and SHALL NOT contact storage.
8. IF storage cannot be reached THEN the API SHALL respond `502`.

**Independent Test**: Start an upload for a 20 MB `.mp4`; receive two part URLs; `PUT` 16 MiB and 4 MiB to them and see storage accept both.

---

### P2: Confirm an upload, exactly once ⭐ MVP

**User Story**: As a user, I want to confirm my upload and get one processing request, even if my confirmation is retried.

**Why P2**: This is where the request is born; duplicates would process the same video twice.

**Acceptance Criteria**:

1. WHEN the owner calls `POST /uploads/:uploadId/complete` with an `Idempotency-Key` header THEN the API SHALL list the uploaded parts in storage, complete the multipart upload, and create one Processing Request whose source key is the upload's key and whose owner is the token's `sub`.
2. WHEN a request is created THEN the API SHALL respond `201` with `{processingRequestId, status}`.
3. WHEN the same user repeats the confirmation with the same key for the same upload THEN the API SHALL respond `200` with the same `processingRequestId` and SHALL NOT create a second request or start a second processing operation.
4. IF the same user uses a key already bound to a different upload THEN the API SHALL respond `409` and SHALL NOT create a request.
5. IF the `Idempotency-Key` header is missing or blank THEN the API SHALL respond `400` and SHALL NOT complete the upload.
6. IF the completed object's size differs from the declared `sizeBytes` THEN the API SHALL respond `400` naming the size, SHALL delete the object, and SHALL NOT create a request.
7. IF no part has been uploaded THEN the API SHALL respond `400` and SHALL NOT create a request.
8. IF the `uploadId` belongs to another user or does not exist THEN the API SHALL respond `404`.
9. WHEN two confirmations with the same key for the same upload arrive concurrently THEN exactly one Processing Request SHALL exist afterwards, and both responses SHALL carry its id.
10. IF the Catalog or storage is unreachable THEN the API SHALL respond `502`, and a retry with the same key SHALL still produce exactly one request.

**Independent Test**: Upload a file, confirm it twice with one key and once with the same key after a failure injected before creation — one request; confirm a second upload with the first key — `409`.

---

### P3: Download my ZIP ⭐ MVP

**User Story**: As the owner of a completed request, I want a download link for its ZIP so that I get my frames.

**Why P3**: It is the product's output; today the ZIP is unreachable.

**Acceptance Criteria**:

1. WHEN the owner calls `GET /processing-requests/:id/download` for a `COMPLETED` request THEN the API SHALL respond `200 {url, expiresAt}`, where `url` is a presigned GET for the request's archive valid for five minutes and `expiresAt` is its expiry.
2. WHEN the owner calls it again THEN the API SHALL issue a new URL.
3. IF the request is not `COMPLETED` THEN the API SHALL respond `409` and SHALL NOT issue a URL.
4. IF the request belongs to another user, does not exist, or the id is malformed THEN the API SHALL respond `404` with the same body as S5's reads.
5. The response SHALL NOT contain `zipStorageKey` or any key as a field.
6. IF the Catalog or storage is unreachable THEN the API SHALL respond `502`.

**Independent Test**: For a completed request, fetch the URL and receive the ZIP; call again as another user and get `404`.

---

### P4: The key-supplied create path is gone

**User Story**: As the product owner, I want creation to happen only through an upload so that no user can point processing at someone else's video.

**Why P4**: It closes S5's recorded risk.

**Acceptance Criteria**:

1. The API SHALL NOT expose `POST /processing-requests`; a call to it SHALL respond `404`.
2. The API SHALL NOT accept a storage key from a client on any route.

**Independent Test**: `POST /processing-requests {sourceStorageKey}` with a valid token → `404`.

## Edge Cases

- WHEN `sizeBytes` is exactly a multiple of `partSize` THEN there SHALL be exactly `sizeBytes / partSize` parts, the last of full size.
- WHEN `sizeBytes` is 1 THEN there SHALL be one part.
- IF a part URL is used after `expiresAt` THEN storage SHALL refuse it (the API does not extend a started upload).
- IF confirmation arrives after the multipart upload was discarded by the bucket lifecycle THEN the API SHALL respond `404` or `400` and SHALL NOT create a request.
- The API SHALL NOT log presigned URLs or their signatures.

## Success Criteria

- [ ] A real MP4 goes up in parts through presigned URLs, is confirmed once, and becomes one Processing Request that reaches `COMPLETED`
- [ ] Retrying the confirmation never creates a second request; a reused key on another upload is `409`
- [ ] The owner downloads the ZIP; another user cannot obtain a URL for it
- [ ] No route accepts a client-supplied storage key

---

## Dependencies

`processing-catalog` UPL-11 to UPL-14 (idempotent create, archive key for the owner) and `fiap-x-platform` UPL-15 to UPL-18 (the API's storage wiring, public endpoint and the multipart lifecycle rule). S5 (authentication) is merged.
